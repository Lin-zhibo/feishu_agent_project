### 用户登录功能 - 结构化需求文档

#### 1. 功能需求 (Functional Requirements)

| 编号 | 需求名称 | 详细描述 | 优先级 |
| :--- | :--- | :--- | :--- |
| FR-1 | 登录入口 | 系统应在应用首页、导航栏或侧边栏提供显眼的“登录”入口。 | 高 |
| FR-2 | 身份凭据输入 | 登录页面应提供以下输入框：<br> - **用户名/手机号/邮箱**：支持用户通过注册时绑定的三种标识之一登录。<br> - **密码**：输入框应支持密码明文/密文切换显示（小眼睛图标）。 | 高 |
| FR-3 | 登录验证 | 当用户点击“登录”按钮后，系统应向后台API发送包含用户名和密码的请求进行验证。<br> - 验证成功：系统需生成有效的会话令牌（如JWT Token），并返回用户基本信息。前端应存储Token并跳转至系统首页或用户请求的原始页面。<br> - 验证失败：前端需在后端返回错误码后，在登录页面上显示清晰的错误提示（如：“用户名或密码错误”）且不清空密码框。 | 高 |
| FR-4 | 登录状态保持 | 系统应支持“记住我”功能。<br> - **勾选“记住我”**：Token的有效期应较长（如7天）。<br> - **未勾选**：Token的有效期应为会话级别（即关闭浏览器后失效）。 | 中 |
| FR-5 | 密码重置 | 登录页面应提供“忘记密码？”链接，点击后跳转至密码重置流程（该流程作为独立功能，此处仅定义入口）。 | 中 |
| FR-6 | 错误次数限制与锁定 | 系统应记录用户IP或账号的连续登录失败次数。<br> - 连续失败5次后，该账号或IP应被临时锁定15分钟。锁定期间，系统应给出友好提示（如：“登录过于频繁，请稍后再试”）。 | 高 |
| FR-7 | 多端登录策略 | 系统需定义：<br> - **单点登录**：同一账号在同一时间仅允许在一个设备上登录。新登录会强制踢除旧会话。<br> - **多点登录**：同一账号允许在多个设备上同时登录（需明确业务规则）。 | 中 |
| FR-8 | 登出功能 | 已登录用户应能通过显眼的“退出登录”按钮主动登出。系统应清除前端保存的Token，并通知后台使Token失效。 | 高 |

#### 2. 非功能需求 (Non-functional Requirements)

| 编号 | 需求名称 | 详细描述 | 指标/约束 |
| :--- | :--- | :--- | :--- |
| NFR-1 | 安全性 | - 密码传输必须使用HTTPS协议加密。<br> - 密码在数据库中必须经过哈希加盐存储（如bcrypt算法），严禁明文存储。<br> - Token需使用安全的签名算法（如HS256, RS256）。<br> - 防止CSRF攻击（如使用SameSite Cookie或Anti-CSRF Token）。<br> - 登录接口应实施接口防刷机制（如CAPTCHA验证码，在连续失败3次后弹出）。 | 通过OWASP Top 10安全扫描 |
| NFR-2 | 性能 | - 登录请求（从用户点击登录到收到响应）的平均响应时间不超过 **2秒**。<br> - 系统应支持 **1000** 个用户同时发起登录请求，CPU使用率不超过70%。 | 平均响应时间 <= 2s |
| NFR-3 | 可用性 | - 登录服务的可用性应达到 **99.9%**（每月停机时间不超过43分钟）。<br> - 登录失败时，前端应提供明确的、用户友好的错误文案，而不是显示技术堆栈错误。 | 可用性 >= 99.9% |
| NFR-4 | 可扩展性 | - 登录鉴权模块应设计为无状态服务，方便水平扩展。<br> - 接入第三方登录（如微信、Google OAuth）时，应遵循Plugin模式，无需修改核心登录逻辑。 | 扩展性设计 |
| NFR-5 | 兼容性 | 登录页面须在以下浏览器中正常工作且UI无错乱：<br> - Chrome（最近2个大版本）<br> - Firefox（最近2个大版本）<br> - Safari（最近2个大版本）<br> - Edge（最新版） | 通过主流浏览器测试 |
| NFR-6 | 日志审计 | 系统应记录每一次登录尝试（成功与失败），包括：<br> - 时间戳<br> - 用户名<br> - 登录来源IP<br> - 操作结果（成功/失败原因）<br> - User-Agent信息 | 日志保留至少180天 |

#### 3. 验收标准 (Acceptance Criteria)

**场景一：正常登录**
- **GIVEN** 用户已经注册了一个有效账号（用户名为 `test_user`，密码为 `正确密码`）。
- **WHEN** 用户在登录页面输入 `test_user` 和 `正确密码`，并点击“登录”按钮。
- **THEN** 系统成功验证用户身份，用户被重定向至系统首页，且页面右上角显示该用户的用户名或头像。

**场景二：错误密码提示**
- **GIVEN** 用户在登录页面输入了有效用户名 `test_user`。
- **WHEN** 用户输入一个错误的密码 `wrong_password` 并点击登录。
- **THEN** 系统不会跳转页面，登录按钮下方或输入框旁显示一条红色提示信息：“用户名或密码错误，请重新输入”。

**场景三：账号锁定**
- **GIVEN** 用户 `test_user` 处于锁定状态（已连续尝试失败5次）。
- **WHEN** 用户输入正确的用户名和密码并点击登录。
- **THEN** 登录依然失败，系统显示提示信息：“您的账号因登录尝试次数过多已被临时锁定，请在15分钟后重试”。

**场景四：记住我**
- **GIVEN** 用户勾选了“记住我”并成功登录。
- **WHEN** 用户关闭并重新打开浏览器，访问应用首页时。
- **THEN** 用户应仍处于登录状态（无需再次输入密码），且Token在7天后才失效。

**场景五：表单校验**
- **GIVEN** 用户没有填写用户名或密码。
- **WHEN** 用户点击“登录”按钮。
- **THEN** 空的输入框下方应出现红色提示：“此项为必填项”，且登录请求不会被发送。

**场景六：HTTPS强制**
- **GIVEN** 用户尝试使用HTTP协议访问登录页面。
- **WHEN** 请求发送时。
- **THEN** 服务器应自动将HTTP请求重定向到HTTPS，确保登录过程全程加密。
